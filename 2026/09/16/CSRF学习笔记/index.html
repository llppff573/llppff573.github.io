CSRF学习笔记

CSRF 跨站请求伪造

CSRF 基本概念与原理

CSRF（Cross‑Site‑Request‑Forgery）跨站请求伪造。
漏洞核心：利用用户已经登录的浏览器会话，诱导用户访问恶意页面，在用户不知情的情况下，携带当前 Cookie 会话，自动发起后端请求，执行非本意的操作。

关键点：攻击者拿不到你的 Cookie，只是借用浏览器自动携带 Cookie 的特性完成请求。
攻击条件：

  1. 用户处于登录状态，会话 Cookie 有效
  2. 目标网站关键操作只依靠 Cookie 身份认证，没有校验 token、验证码、Referer 等
  3. 诱导用户打开攻击者构造的恶意页面

可实现攻击行为：

  1. 修改用户密码、修改个人资料
  2. 执行转账、提交留言
  3. 修改账号绑定手机号

⚠️安全提醒：仅允许在授权靶场练习，禁止测试非授权站点。

CSRF 与 XSS 简单区分

  • XSS：执行 JS，窃取 Cookie，在攻击者视角发起请求
  • CSRF：不执行 JS，借用浏览器自动带 Cookie，以受害者身份发起请求，拿不到 Cookie 内容

CSRF 实验（pikachu 靶场）

CSRF‑GET 型

  1. 登录靶场账号，进入修改个人资料页面，修改任意一个信息，本次将地址改为：aaaa，观察修改信息抓包。
    请求为 GET 请求，参数直接放在 URL 中，没有 token 校验。

  2. 复制这次get请求的URL，构造恶意 URL，修改参数，用来篡改用户信息，本次修改的是地址信息，改为beijing。

  1. 当已经登录的受害者访问这条 URL，浏览器自动携带 Cookie，直接完成资料修改。我们假设我们是lucy，在浏览器中访问这个url。访问后发现lucy的地址变成立beijing。

特点：GET 型 CSRF，所有参数放在 URL，构造简单；很多现代网站关键操作不再使用 GET 做修改操作。

CSRF‑POST 型

  1. 修改资料功能使用 POST 提交表单，将地址改为shanghai，找到其对应的数据包。

  2. 把整个 Cookie 头删掉，直接发送 Repeater 重放。

  3. 回到靶场刷新个人信息：资料依旧被修改

CSRF Token 防护机制

  1. 页面表单每次渲染生成随机、不可预测的csrf_token，随表单一起提交。
  2. 后端校验本次请求携带的 token 和 session 内存储 token 是否一致。
  3. 攻击者无法获取页面内随机 token，就无法伪造完整请求，防御 CSRF。

pikachu 靶场带 token 的关卡：直接复制上面 POST 恶意表单，缺少合法 token，请求会被后端拒绝，攻击失效。

CSRF 绕过思路（靶场练习）

  1. 还是登录lucy这个账号，修改数据（本次修改住址为：wuhan）然后到bp里面找到抓的包，将本次请求复制下来。发现这次多了一个token值。

  2. 打开页面，进行检查，刷新发现每次进入页面都会访问token_get_edit.php文件，并且可以检查中看到对应的值。

CSRF 防御方案

  1. 核心方案：使用 CSRF‑Token
    关键操作表单每次生成随机 token，存入 session，提交请求校验 token 一致性。
  2. 校验 Referer 请求头（辅助，不做唯一防御）
  3. 关键操作增加验证码，强制用户交互
  4. 关键操作二次输入密码确认
  5. 配置 SameSite Cookie 属性，限制第三方站点请求携带 Cookie

CSRF 总结

  1. CSRF 本质：浏览器 Cookie 会同源自动携带，网站只依靠 Cookie 鉴权。攻击者无法获取 Cookie 明文，只是借用会话身份。
  2. GET‑CSRF：构造恶意 URL，img 标签自动触发；POST‑CSRF：构造自动提交的恶意表单页面。
  3. Token 是最有效防御手段；没有 token 防护，仅靠 Referer 防护存在被绕过风险。
  4. 和 XSS 的关系：如果同时存在 XSS 漏洞，可以直接读取页面 csrf_token，直接绕过 CSRF 防御。
  5. 实验踩坑：复现必须保证受害者浏览器处于登录状态，会话 Cookie 有效；浏览器 SameSite 策略会影响复现效果。
